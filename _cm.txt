fix: make registration atomic (user + starter seed in one transaction)

registerUser inserted the user row, then called seedNewUser (starter wallet +
9 system categories) as two separate, untransacted inserts. A failure between
them created an account that could log in but had no wallet and no categories
— permanently broken, because nothing in the app ever re-runs the seed.

Fixed by running both inside one db.transaction(). seedNewUser now accepts an
optional tx handle; password hashing deliberately stays OUTSIDE the
transaction, since bcrypt is slow and would hold a connection open ~100ms
under load.

test:register:atomic proves atomicity rather than assuming it, in two steps:
  1. Replicate the OLD behaviour with a forced mid-way failure -> a user row
     IS left behind (so the failure mode is real, not theoretical).
  2. Replicate the NEW behaviour with the same failure -> no row survives.
If step 1 ever stops leaving a row, the test says so instead of passing
vacuously.

test:newuser-seed adds a scan for any EXISTING user missing a wallet or
categories. It currently reports 7 leftover test fixtures, which are inserted
straight through SQL and legitimately unseeded — so the check distinguishes
fixtures from real signups rather than failing on its own debris.
