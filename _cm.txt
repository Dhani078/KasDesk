fix: check Content-Length before buffering the OCR upload

await req.formData() reads the ENTIRE request into memory, and the 10 MB
file.size check ran only AFTER that. So a multi-hundred-MB upload was buffered
into RAM and then rejected — a memory DoS, made cheap by the route's 20
requests/min per-user budget.

Fixed with a Content-Length pre-check before parsing. The header is advisory
(a client may omit or lie), so the file.size backstop stays as the real gate;
the pre-check exists purely so the common case never reaches the buffer.

Measured after the fix: an 11 MB upload is refused with 413 in ~139ms.

The test asserts the guard's PLACEMENT, not just its presence, because a
Content-Length check after req.formData() would be useless — the body would
already be in memory. That assertion initially failed for the wrong reason:
it matched the string "req.formData()" inside the guard's own comment rather
than the call. Now it searches for "await req.formData()".

Also worth recording: the first version of this test drove the route over
HTTP with a forged Content-Length, and curl refuses to send a header that
disagrees with the body, so the request never left and every case "passed".
The OpenAI-style fake-action-id test from earlier had the same shape of
mistake. Structural + timing assertions replaced it.
