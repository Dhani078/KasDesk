fix: send the Gemini key as a header, not in the URL query string

The route built its upstream URL as `${ENDPOINT}?key=${apiKey}`. A query
string is a leak vector the application's own logs never reveal:

  - proxy and CDN access logs record full URLs
  - any fetch error that echoes the request URL carries the key with it

Now sent as the x-goog-api-key header.

Verified against the LIVE endpoint rather than assumed, using a control:
  - valid key via header  -> 429 (quota exhausted, i.e. the key was accepted)
  - invalid key via header -> 400 "API key not valid"
Different answers prove the header is actually read. A test without that
control would pass against an endpoint that ignored the key entirely.

The test asserts both halves: structural (no `?key=` in the route, key not
logged) and behavioural (the live control above). It skips loudly, rather than
passing, when GEMINI_API_KEY is absent.

Note: the 429 also confirms the key itself is still valid — the free-tier
quota for gemini-2.5-flash is simply exhausted right now, which is why the
real-OCR suite reports SKIPPED.
