fix: reject transactions against archived wallets at the source

Real defect found by auditing the ledger, not from the PRD list.

An archived wallet is excluded from Total Saldo by design. getWallets()
filters isArchived=0, so the UI never offers one — but createTransaction()
did not reject it. Any spend against an archived wallet therefore made money
leave the ledger with no visible trace: Total Saldo is unchanged (the wallet
is invisible) but the balance really did drop.

Measured with a fixture: active-only sum stays 1000000 while all-wallets sum
drops to 1600000. The 400000 is gone and nowhere on screen.

Fixed by throwing WALLET_ARCHIVED for BOTH the source wallet and the transfer
destination — an archived destination swallows money the same way. Surfaced as
a clear Indonesian message rather than a generic failure.

Two notes on how this got tested:

1. The rule lives in lib/wallet-guard.ts, not lib/actions.ts. actions.ts is
   'use server', which requires every export to be async — a plain exported
   helper breaks the build with "Server Actions must be async functions".
   It also cannot be imported from plain Node because requireUserId() needs a
   Next request scope. Extracting it made the rule unit-testable (12 checks,
   covering the 0/1/boolean/string/Buffer shapes MySQL may return for tinyint,
   plus null-safety so a NULL column cannot block every transaction).

2. The DB-level test asserts the invariant the guard protects rather than
   faking an authenticated request, which would have passed vacuously on
   UNAUTHENTICATED.

186 checks green across 19 suites.
