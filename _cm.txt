feat: security headers for all routes

Responses carried NO security headers at all. For a finance app the sharpest
gap is framing: a look-alike site could iframe the app for clickjacking.

Added to next.config.ts for every route:
  X-Content-Type-Options: nosniff
  X-Frame-Options: DENY
  Referrer-Policy: strict-origin-when-cross-origin
  Permissions-Policy: microphone=(), geolocation=()
  Content-Security-Policy-Report-Only (see below)

Two deliberate choices:

1. CSP is REPORT-ONLY, not enforcing. A strict policy has to account for
   Next's inline bootstrap scripts, the PWA service worker and Tailwind's
   runtime; a wrong enforcing CSP either breaks the app or gets disabled by
   the first person it blocks. Report-only surfaces violations in the console
   with zero risk, and can be promoted once those reports are clean. The test
   asserts an enforcing CSP has NOT appeared, so this cannot be flipped by
   accident.

2. Camera is not in Permissions-Policy. The receipt scanner uses a <input
   type=file capture>, not getUserMedia, so no camera permission is needed and
   adding camera=() would have been a wrong claim (and could break the native
   "take photo" flow).

The test checks both presence AND that the app still functions — a bad header
can satisfy the first while breaking the second. It also asserts signed-out
/ still redirects, so headers cannot silently bypass auth. That last check
caught a bug in the test itself: an early version called / without the session
cookie and wrongly reported a failure.
