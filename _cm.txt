fix: lost-update race in balance mutation (defect 11.4)

THE BUG
Balance updates used read-modify-write: SELECT the balance, then
UPDATE with the value just read. Two concurrent expenses both read the
same starting balance and the second write silently overwrites the
first — money disappears with no error and no log line.

Measured on the live TiDB instance (scripts/test-concurrency.js):
10 concurrent Rp 1.000 withdrawals from a Rp 10.000 balance left
Rp 8.000 instead of Rp 0. Eight transactions vanished.

THE FIX
Use atomic SQL expressions so the database does the arithmetic:
  SET balance = balance - ?   instead of   SET balance = <read> - ?
Applied to createTransaction (income/expense/transfer) and
deleteTransaction (all three reversal paths), via drizzle `sql`.

Also fixed
- createTransaction returned `row.insertId ? ... : crypto.randomUUID()`.
  insertId is only meaningful for auto-increment keys; our PK is a
  client-generated UUID so it always fell through to a random UUID that
  matched no row. The id is now generated up front and returned.
- TRANSFER no longer re-SELECTs the destination balance (that read was
  also racy); both legs are now atomic.

Tests added
- scripts/test-balance.js (14 checks): income, expense, transfer
  conservation, overdraw refusal, rollback, delete-reversal, negative
  invariant, int64 precision at 9.000.000.000.000
- scripts/test-concurrency.js: proves the hazard and the fix
- scripts/test-balance-e2e.js (8 checks): drives the real Server Action
  over HTTP; asserts the UI figure equals the DB figure
- package.json: test:balance, test:balance:e2e, test:concurrency

PRD: defects 11.3 and 11.4 marked FIXED with evidence.

Results: tsc clean, build green, balance 14/14, e2e 8/8,
concurrency 2/2, smoke 19/19, isolation 10/10.
